# 🧠 Project Overview: Intelligent Query Router

## 📌 Executive Summary

The **Intelligent Query Router** is a modular multi-agent workflow system built using **LangGraph**, **LangChain**, and modern Large Language Models (LLMs). It acts as an intelligent traffic controller for AI applications—dynamically evaluating user prompts, classifying user intent, and routing requests to specialized domain experts or external search tools.

---

## 🔍 1. Problem Statement

### The Pitfall of Monolithic Single-Prompt Systems
In conventional AI applications, a single prompt is tasked with answering every type of question:
* Writing complex Python code and calculating Big-O complexity.
* Answering queries about live real-world events and breaking news.
* Engaging in open-ended creative writing, brainstorming, and customer support.

### The Consequences:
1. **Prompt Congestion & Bloat**: Packing multiple domain guidelines into one massive prompt confuses the model and degrades adherence to instructions.
2. **High Token & API Costs**: Triggering search tools or heavyweight reasoning prompts on simple greetings wastes computational resources and money.
3. **Inconsistent Outputs**: A prompt tuned for casual conversation fails when asked for strict code formatting, and vice-versa.
4. **Hardcoded Spaghetti Code**: Traditional rule-based routing using keywords (`if "code" in query:`) is fragile, fails on ambiguous semantics, and cannot scale.

## 🏛️ 2. Architectural Design & Philosophy

The Intelligent Query Router solves this through **Separation of Concerns (SoC)** using graph-based orchestration.

## ⚙️ 3. Core Technical Components

### A. Central State Contract (`RouterState`)
State in LangGraph represents the single source of truth across all graph executions.
```python
class RouterState(TypedDict):
    messages: Annotated[list, add_messages]  # Conversation history
    destination: str                         # Routing key determined by classifier
    query: str                               # Input query from user
    response: str                            # Final output generated by the selected node
```

### B. Classification Engine (`router_node`)
The classification node uses **Pydantic Structured Outputs** to guarantee deterministic schema conformance:
```python
class RouteQuery(BaseModel):
    destination: Literal["code_expert", "web_search", "general_assistant"] = Field(
        description="Select the most appropriate node destination."
    )
    reasoning: str = Field(description="Explanation of routing decision.")
```
* **Strict Type Safety**: The LLM output is strictly bounded to the `Literal` destinations.
* **Explainability**: Returns explicit `reasoning` describing why a path was chosen.

### C. Specialized Worker Nodes
Each worker node operates in isolation with dedicated system instructions:

| Worker Node | Domain Focus | Purpose & Optimization |
| :--- | :--- | :--- |
| **`code_expert`** | Programming & Algorithms | Generates robust, production-ready code with time/space complexity analysis, typing, and edge case coverage. |
| **`web_search`** | Fresh & Factual Knowledge | Geared toward real-time news, sports scores, and search queries (integrable with search APIs like Tavily). |
| **`general_assistant`** | Conversational & Creative | Friendly, helpful tone optimized for brainstorming, explanations, and creative writing. |

### D. Conditional Routing Mechanism (`add_conditional_edges`)
Instead of hardcoding routing logic inside node functions, LangGraph allows declarative conditional transitions:
```python
def route_decision(state: RouterState) -> str:
    return state["destination"]

builder.add_conditional_edges(
    "router",
    route_decision,
    {
        "code_expert": "code_expert",
        "web_search": "web_search",
        "general_assistant": "general_assistant",
    }
)
```

## 🔄 4. End-to-End Execution Lifecycle

1. **Ingestion**: The user passes a query (e.g., *"Write a Python function to reverse a linked list in O(n) time"*).
2. **Intent Classification**: The `router` node invokes the classifier schema. It identifies the query as technical and outputs `destination="code_expert"`.
3. **Dynamic Dispatch**: LangGraph evaluates `route_decision` and triggers `code_expert_node`.
4. **Domain Execution**: `code_expert_node` generates code with documentation and complexity analysis.
5. **State Aggregation**: The clean response is stored in `state["response"]`.
6. **Output Delivery**: The response is rendered with Markdown auto-wrapping without horizontal scrolling.

---

## 🌟 5. Key Advantages & Benefits

* 🎯 **Maximum Accuracy**: Domain-specific prompts yield significantly higher accuracy than generic catch-all prompts.
* ⚡ **Cost & Latency Efficiency**: Lightweight routing models classify quickly, invoking heavy tools only when necessary.
* 🧩 **Extensibility**: Adding a new expert (e.g., `math_agent`, `sql_agent`, `rag_docs`) requires only adding a new node and updating the Pydantic enum.
* 🛠️ **Maintainability**: Clean visual DAGs (Directed Acyclic Graphs) eliminate complex, error-prone nested conditional statements.
